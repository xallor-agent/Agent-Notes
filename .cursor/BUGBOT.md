# Agent-Notes Bugbot 规则

本仓以技术博客、教程和笔记为主。审查目标是内容正确、读者能理解、操作可复现。

用简体中文评论，只报告有依据的实质问题。

## 审查范围

- 先判断文章用途：概念讲解检查推理与例子；操作教程检查前提、步骤和结果；参考资料检查定义与版本。不强制所有文章采用同一种结构。
- 阅读变更及必要上下文，报告本次新增、加重或因变更产生的关联问题；避免无关的全库整改。
- 仓库中的脚本和配置仍需检查实际行为，不能因其用于教学就忽略功能错误。

## 内容检查

1. **读者与结构**：标题和正文是否一致；理解或操作所必需的术语、前提是否先说明；是否存在影响理解的跳步、重复或无关背景。面向公众的教程应自包含，不依赖作者与 Agent 的会话、个人账号或未交代的项目历史。
2. **技术正确性**：概念、公式、图示和代码是否一致；符号、单位、维度、假设和适用范围是否明确；示例是否真正支持结论。区分事实、推断与类比。
3. **来源与时效**：关键技术结论、数据和引用是否有可核对的依据，优先原始论文、官方文档或源码；按对应版本核对，区分源码存在、正式发布、集成可用和实际运行通过；搜索无结果不能单独证明功能不存在。“最新”“已支持”等时效性结论应限定日期或版本。保留复现所需的版本信息，不要求常识性陈述逐句引用。
4. **操作闭环**：教程是否给出必要的环境、依赖、权限、输入和执行顺序，以及关键步骤的预期结果或成功判据；命令中的工作目录、Shell、占位符和变量是否交代清楚。区分完整可运行示例与代码片段、伪代码，不把省略内容当作可直接复制执行的代码。
5. **证据与声明**：静态核对、局部测试、端到端运行和效果评估是否被准确区分；正文结果是否对应当前脚本与条件。未实际执行的命令或测试，不得声称已验证通过；无法核查时说明缺少的证据，不把未知判成错误。
6. **文件与呈现**：本地链接、图片、附件和标题锚点是否能解析；移动或删除文件时检查受影响的引用。按仓库实际使用的 Markdown/Obsidian 语法判断，接受有效的 `[[wikilink]]`。检查代码围栏、表格和公式语法；图中符号、箭头和数值应与正文一致，关键含义需有文字说明。未查看渲染结果时，不断言图片清晰或公式渲染正常。
7. **元数据与公开内容**：保留已有 frontmatter，检查标题、日期、状态与正文是否矛盾，不凭空新增字段规范。报告真实密钥或不应公开的个人信息；明确的示例占位符可接受。

GitHub Preview 是公开文章的阅读入口。对新增或修改的数学公式，报告已知会导致渲染失败的写法：当前 `\operatorname{...}` 会被 GitHub 拒绝；带括号的函数名可用 `\mathrm{...}` 保留含义。检查行内公式、`$$` 公式块和 `math` 围栏；不误报行内代码或普通代码围栏中用于讲解语法的文本。其他命令需有渲染失败证据，不能仅因陌生而禁止。

## 评论格式

每个独立问题只评论一次，定位到相关变更行，并包含：

- 文件路径（及标题/行附近位置）
- 为什么这是问题、对读者的具体影响及判断依据
- 可执行的修改建议，必要时提供替换文本或命令。

优先报告导致错误理解、操作失败或敏感信息泄露的问题。没有充分依据或只有个人偏好时不评论；不重复已有且仍适用的审查意见。若现有 CI 已明确报告同一问题，不重复报错；未确认有自动检查时，不假定它已覆盖。

## 不要做

- 不要因为用词偏好、排版口味发评论，或要求每篇文章增加目录、总结、图片和固定章节。
- 不要把合理的教学简化写成“实现不完整”，或要求所有示例达到生产级异常处理、优化和测试覆盖；简化导致错误结论或步骤无法执行时应指出。
- 不要批准 PR、不要改代码、不要开修复分支（除非用户明确要求 Autofix）
